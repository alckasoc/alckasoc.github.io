Architecture & serving

  • Config. Hugging Face card tags 763B parameters total; tensors in BF16, F32, F8_E4M3, and I8. Image-text-to-text and text-generation tags set.

  • Context and output. 1M-token context window; max output 384K tokens; concurrency limit 2,500; thinking mode default (non-thinking mode supported).
  • Endpoints. OpenAI format at https://api.deepseek.com; Anthropic format at https://api.deepseek.com/anthropic. Vision supported on deepseek-flash, not on the retired deepseek-v4-pro alias.
  • Serving stack. vLLM, SGLang, Docker Model Runner. No Jinja chat template in the card; a Python reference implementation plus the deepseek-recipe Rust library with Python bindings for production.

Pre- and post-training

  • No pretraining change. The config.json matches V4.1-Flash. The release note explicitly frames the gains as agent-shaped post-training, not fresh pretraining.
  • Reinforcement learning with self-feedback. The release note names "RL with self-feedback" and links it to end-to-end project development (plan → code → tool call → iterate). Named Contributions & Mechanisms

  • RL with self-feedback for in-architecture agentic refinement.
    • Problem. A new pretraining run on a 763B-tagged MoE at deepseek-v4-pro's scale is prohibitively expensive to repeat on a sub-two-month cycle, but the agentic workloads — terminal use, repo-scale coding, project-end-to-end — are where frontier open models now compete. The gap is a cheap way to lift agentic resolve rates on a frozen architecture without touching pretraining tokens or MoE routing.
    • Mechanism. DeepSeek names the update as reinforcement learning with self-feedback: the model's own trajectories on multi-step tasks (plan → write code → run → observe → iterate) are used both to produce the training signal and to score it, with no new base architecture. The config.json match confirms there is no new expert count, routing scheme, or layer rebalancing. The post-training pass goes into tool-use trajectories specifically, which is why Terminal-Bench 4.0 jumps +11.1 and ProgramBench jumps +8.8 while fixed-answer ZeroBench-main moves only +2.0.
    • Why it works. Keeping architecture frozen means the V4.1-Flash inference stack (vLLM/SGLang configs, kv-cache layouts, serving infrastructure, pricing tiers) carries over without change — the alias deepseek-flash picks up 1017 transparently. Routing a dedicated RL pass through the agentic trajectory distribution is cheaper than co-training on static pretraining data and amplifies the delta precisely where the product is sold, versus the Opus 4.8-era approach of a single-pass RLHF polish on top of SFT (same architecture family, same base model, delta captured by downstream RL).
  • Search & Fetch API as a managed agent primitive.
    • Problem. Open-weight model vendors have no answer to the Grok Voice 3.0 / GPT-Realtime pattern of first-class web_search and file_search tools inside the serving endpoint. A developer wiring up a V4.1-Flash agent for research-style queries either re-implements search from scratch (brittle), pays a third-party per request (expensive, unpredictable), or scrapes the app surface (fragile).
    • Mechanism. The Search & Fetch API exposes the retrieval-and-rendering pipeline that already backs the DeepSeek app at $0.75/1k successful calls, with a 2026-10-31 billing-start window to let integrators migrate. The retrieval stack returns both ranked results and fetched content, so a V4.1-Flash agent in thinking mode can call it like any other tool without a RAG scaffolding.
    • Why it works. Pricing search per successful call — not per attempt — prices against the result rather than the probe, which matches how a thinking-mode agent retries. The pairing with the DeepSeek Harness preview (DeepSeek's internal harness, now developer-accessible) completes a serving-plus-tooling triangle around deepseek-flash that mirrors what closed-weight vendors ship as a single realtime endpoint, but at open-weight pricing.

Named Contributions & Mechanisms

  • 256-expert MoE with 8 active, under a Perception Encoder for vision.
    • Problem. Open-weight frontier contenders have landed on two conflicting tradeoffs: Chinese open models (Kimi K3, GLM 5.3, Qwen3.8) favor dense-ish MoE with fewer experts and higher activation ratio for coding sharpness; smaller US open releases (Nemotron 3.5 Bolt 74B-A9B) sit at the lower end for device-fit. Meta's bet is on headroom — 42B active is competitive with closed frontier inference compute while 816B total keeps knowledge capacity above everything open.
    • Mechanism. 256 experts per MoE layer, 8 active per token, over a 62-layer backbone with grouped-query attention and QK-norm. Vision enters through a dedicated 1.8B-parameter Perception Encoder whose embeddings are consumed by the main model, not through interleaved layers — which keeps the text pathway unperturbed when images are absent and lets Meta scale the vision encoder independently of the backbone.
    • Why it works. Keeping the vision stack separate from the MoE layers avoids a Mobius-style decoupled-knowledge-vs-reasoning routing problem (see prior review 2026-08-17): image conditioning does not consume routed-expert capacity that would otherwise go to language experts. The 8-of-256 activation ratio is sparser than Qwen3's standard route and leaves more headroom for domain specialization without inflating the active-parameter bill — which is how JobBench 61.8 and MCP-Atlas 89.2 clear the Chinese cluster at parity-ish active compute.
  • Muse Model License as a staged open-weight contract.
    • Problem. Apache 2.0 lets a MaaS vendor rehost without any obligation to the model author, which is why Chinese open weights (Kimi K3, GLM 5.3, Qwen3.8) are freely hosted by every inference-provider under their own branding. Meta wants redistribution-friendly terms (for research adoption, local inference, downstream fine-tunes) without underwriting a competitor's hosted-API margin for free.
    • Mechanism. The license has three layers. Attribution: "Built with Muse Spark Open" required in any product-visible surface. Revenue clause: hosted services over $20M/12 months must notify Meta and sign a separate agreement. Internal and own-product use is exempt from the revenue clause, so an enterprise embedding Muse Spark Open in its product never hits the trigger. Hugging Face gating captures the trained identity of every downloader.
    • Why it works. The $20M threshold is set well above hobbyist and research use but intercepts commercial inference-provider adoption. The identity-gated Hugging Face flow (full legal name, date of birth, organization — non-editable after submission) is the enforcement surface: Meta can map any downstream commercial deployment to the original downloader. The MaaS carve-out is specifically what makes Kimi/GLM/Qwen Apache 2.0 release pricing (which has driven open-weight hosted margins toward zero) harder to replicate against Muse Spark Open at scale.
  • NVFP4-first Blackwell-targeted release format.
    • Problem. BF16 at 816B is ~2TB of VRAM — outside the single-node footprint of most 2026 GPU installs and nearly all local hardware. INT8 PTQ on this scale regresses measurably on coding benchmarks; W4A16 is unevenly supported.
    • Mechanism. Meta ships NVFP4 weights day-one alongside BF16. NVFP4 is Blackwell's native 4-bit floating-point format with per-group FP8 scales; Muse Spark Open NVFP4 lands at ~700GB VRAM / ~493GB on disk, a ~2.9x shrink over BF16. Apple MLX is also day-one supported, with the full model split across two 512GB M5 Ultra Mac Studios over Thunderbolt 5 with RDMA, or four 256GB ones — >36 tokens/sec on a four-Mac rig at 8,192-token context.
    • Why it works. NVFP4 preserves the vector of per-channel scaling that INT4 PTQ loses; on Blackwell, matmul kernels run FP4×FP4 natively, so a BF16-trained-NVFP4-cast weight ships at ~2.9x smaller without a round of post-training quantization-aware recovery. The result is a day-one 700GB deployment that fits a single DGX Blackwell node, and a $43,196 four-Mac rig that runs the full model locally. Nemotron 3.5 Super VL took a related path (Bolt 74B-A9B is native 2-bit, trained for the quantized format from the start) — Muse Spark Open is the 816B analogue at 4-bit.

Safety & limitations

  • Meta reports released-checkpoint-only safety numbers: 99.2% cyber refusal, >98% CBRN refusal in some tests, 98.1% MASK honesty, and recommends deployment behind additional system-level guardrails.
  • Not intended for users under 18. Multi-step reasoning errors and small quantized-vs-BF16 quality differences flagged.
  • Training data is not fully disclosed (public, crawled, third-party, Meta-derived, synthetic). No tokens-per-modality figures. No RL algorithm or SFT dataset size published.
  • Beijing's proposed export controls on open-weight models at 2T+ parameters do not apply retroactively to Kimi K3 and Qwen3.8; the clause's threshold is roughly 2.5× the Muse Spark Open total, so no symmetric constraint applies to Meta's release.
  • Pattern vs 2026-04 Llama 4 controversy (Meta promoted a leaderboard score from a non-released checkpoint): Meta's AA Index 39 figure remains uncorroborated by Artificial Analysis itself as of 2026-10-15.

Named Contributions & Mechanisms

BlenderWorld: Benchmarking Visual Agents for 3D Creation from Real-World References

Tier 2 · Research Paper arXiv · Qwen (Alibaba) + Zhejiang Univ. + CUHK + Fudan + NTU 2026-10-19 (arXiv) 3D creation · Benchmark · Visual agents · Blender · Multimodal

Overview

  • Alibaba Qwen, with collaborators at Zhejiang University, CUHK, Fudan, and NTU Singapore, published BlenderWorld on arXiv as 2610.23986 (Hugging Face Daily, 2026-10-20). The benchmark evaluates multimodal LLMs on realistic 3D creation tasks in Blender using photo, video, or specification-file references — a shift from text-only prompts.
  • Headline finding: even the leading model (GPT-6-Astra) fully satisfies every fine-grained requirement on just 42.2% of tasks and reaches a fused score of 79.9/100; Opus-5 comes next at 73.0 and GPT-5.6-Sol at 67.7.
  • Framework/evaluation code is on GitHub at QwenLM/BlenderWorld under MIT; dataset on Hugging Face at Qwen/BlenderWorld.

Methodology

  • Benchmark construction. 223 tasks across 9 categories and 22 subcategories (products, architecture, natural environments, characters, animation, scientific visualization, vehicles, simulation, scenes). Input mix: 130 image-plus-text tasks, 15 video-plus-text tasks, 78 text-only tasks, 59 with specification files (dimensions, materials, camera settings).
  • Criteria. 2,651 binary acceptance criteria extracted by multimodal models and verified by at least two independent judges, then frozen as weighted (3/2/1) checks (6–22 per task). The generating agent cannot see the criteria.
  • Submission format. Agents must deliver an editable Blender project saved as model-output/final.blend, not a rendered image. The .blend files are the primary artifact scored.
  • Evaluation harness. bw prepare builds per-task workspaces; agents produce .blend files; bw pack-submission bundles outputs; bw evaluate renders and scores. Rendering: 8 adaptive camera views, Cycles backend at 1024×1024 with 64 samples. Environment pinned at Blender 4.2.10, Python 3.10+, Codex CLI 0.147.0, Claude Code 2.1.220.
  • Dual-track review.
    • Visual (VLM judge). Judges the 8-view renders and video for appearance, layout, and motion (13 rubric aspects: geometry, spatial layout, materials, functionality, etc.).
    • Structural (agent judge). Inspects the .blend file's internal structure and properties with tools, which catches exact-dimension requirements and other spec-level checks that renders cannot show.
    • Fused score. Overall = 0.5 × Rubric + 0.5 × Dimension, with a Perfect-pass rate reported separately. Submissions without a .blend project score 0 but stay in the denominator.
    • Public harness runs Cycles on CPU with no score cap; the paper setup used GPU. Published scores from the paper and locally obtained scores may differ.

Named Contributions & Mechanisms

  • Editable-artifact scoring: .blend file is the submission, not a render.
    • Problem. Image-generation benchmarks score a rendered picture, which lets an agent "paper over" bad geometry with surface shading or clever camera framing. For 3D creation that is downstream work (animation, simulation, VFX), the editable project is what matters: dimensions, materials, modifier stacks, rig topology. A render-only benchmark does not test any of that.
    • Mechanism. BlenderWorld requires the submission to be an editable .blend file saved to model-output/final.blend. The structural judge opens the project in Blender and inspects its internals with tools (bpy.data-level queries over objects, materials, armatures, modifiers), separately from the VLM judge that scores rendered views. A model that produces a visually plausible scene but hides geometry in a child collection fails the structural half.
    • Why it works. Splitting Rubric and Dimension at 0.5/0.5 prevents either half from dominating; a model that can shade well but cannot assemble a dimensioned asset is capped at 50. The dual-track design maps onto the actual downstream workflow of a 3D artist — the .blend file is handed off, not the final render — which is what makes 42.2% perfect-pass a stricter ceiling than the 13-rubric visual score alone would deliver.
  • Reference-anchored tasks across text, image, video, and spec inputs.
    • Problem. Text-only prompting for 3D creation lets the agent fall back on scene-level priors (a "chair" is any chair). Benchmarks built on open-text prompts have a ceiling set by how specific the prompter is willing to be, which lets strong-text models hit high scores without really doing 3D creation.
    • Mechanism. 130 image, 15 video, 59 spec-file tasks anchor the required output to a specific target: a photographed room, a filmed object in motion, or a specification file listing exact dimensions, materials, and camera settings. The criteria extraction (2,651 binary rubrics) is run on the reference, not the prompt, so an agent that reproduces the generic concept but misses a reference-specific feature fails the corresponding criteria.
    • Why it works. The +8.6-point multimodal gap for GPT-6-Astra over Opus-5 on image/video inputs is exactly this effect: strong-vision models can anchor to the reference and reproduce specific details, while weaker-vision ones default to a generic rendering. Pairing this with the .blend editable-artifact requirement makes it the strictest 3D-creation benchmark that current frontier models have been scored on, with headroom to 100 on both halves.

DeOverlay: A Benchmark and Source-Anchored Flow for Video Overlay Removal

Tier 2 · Research Paper arXiv · ByteDance Seed 2026-10-19 (arXiv; HF Daily 2026-10-20) Video · Flow matching · Overlay removal · Benchmark

Overview

  • ByteDance Seed (Deshui Miao, Yuhang Ma, Shaoyong Jia, Wenzhao Gao, Yue Zhang, Shaohui Jiao, Xin Li) released DeOverlay on arXiv as 2610.26081 on 2026-10-19 (Hugging Face Daily, 2026-10-20). The paper has two deliverables: a DeOverlay model (source-anchored flow matching for video overlay removal) and DVTE-Bench, a paired-video benchmark of 1,631 clips and 136,090 frames across 8 text-overlay categories.
  • Core framing: temporal-propagation and source-conditioned-generation methods either leave residual overlays or distort scene structure when source information is hidden. The paper's bet is on anchoring the generative process to the overlaid source latent while running flow-matching along learned source-to-clean paths, which allows successive corrections from intermediate states.

Methodology

  • DeOverlay model.
    • Source-anchored flow: the model starts from the source (overlaid) latent and iteratively refines toward a clean latent along a learned flow path. The source guidance is fixed throughout, not re-sampled per step.
    • Region-weighted flow matching: a shared velocity network trained on paired source-to-clean paths, with weighting concentrated on the masked regions. Successive corrections are issued from intermediate flow states, not only from the full source.
    • Visibility-normalized temporal aggregation: local source cues are gathered by excluding masked positions and averaging the visible observations over time, so the flow receives a cleaner estimate of what the scene looks like under the overlay.
    • Additive conditioning: global source context and edit-region embeddings are added to the latent without lengthening the video-token sequence, which keeps the compute envelope on par with ordinary video diffusion.
  • DVTE-Bench construction.
    • 1,631 paired clips (overlaid / clean), 136,090 frames, 8 text-overlay categories, 91.1 minutes of video, every clip with audio. 1,085 portrait (66.5%) / 546 landscape (33.5%). 11 language labels.
    • OCR-screened clean targets: 569 candidate pairs were rejected by the target-side OCR audit to prevent clean videos from containing residual text that would contaminate scoring.
    • Frame-aligned pixel masks per clip, with common evaluation protocol.
    • Metrics: Mask PSNR, SSIM, LPIPS, DISTS, VFID, TWE, TC, flow statistics.

Evaluation & Results

  • DeOverlay outperforms four baselines on all five reconstruction and perceptual metrics that the arXiv page highlights.
  • vs the strongest baseline: Mask LPIPS -58.3%, Mask VFID -70.3%.
  • Qualitative results demonstrated on graphic logos and stickers, not just text subtitles.
  • Full per-method per-metric table is in the paper and in data/results.csv on the project site; it was not loaded in the HTML surface rendered without JavaScript.

Named Contributions & Mechanisms

  • Source-anchored flow with region-weighted matching.
    • Problem. Prior overlay-removal methods pick one of two bad options. Temporal-propagation methods (frame-to-frame inpainting) leave residual overlay in frames with motion or occlusion, because the propagation smears the overlay signal rather than suppressing it. Source-conditioned generative methods (ControlNet-style conditioning on an overlay-free guide) distort scene structure when the overlay occludes a key feature, because the generator has no counterfactual to work from.
    • Mechanism. The DeOverlay flow starts from the overlaid-source latent, not from pure noise. Flow matching trains a shared velocity network on paired source-to-clean paths, with region weighting that concentrates loss on the overlay region. At inference, the model issues iterative corrections from intermediate flow states, so each step refines against the running estimate rather than against pure noise or against the fixed source.
    • Why it works. Anchoring the flow at the source latent means every refinement step is coherent with the unmasked region, which is where temporal-propagation methods lose structure. Region weighting concentrates capacity where it is needed; successive corrections from intermediate states amortize the heavy lifting across the flow path rather than concentrating it at a single denoising step. The Mask LPIPS -58.3% and Mask VFID -70.3% deltas against the strongest baseline on DVTE-Bench are consistent with that mechanism: the perceptual metrics on the masked regions are precisely where the paper's weighting concentrates capacity.
  • Visibility-normalized temporal aggregation.
    • Problem. Averaging frames to get a cleaner source estimate biases the result toward frames where the overlay happens to cover more pixels — those frames contribute masked (and so garbage) signal to the average, which the generator then has to walk back.
    • Mechanism. Visibility normalization: for each pixel location, the aggregation averages only the frames where that location is not masked, normalizing by the visible-frame count. Masked positions are excluded from both the sum and the normalizer.
    • Why it works. This gives the flow a time-aggregated estimate of the scene whose variance is lowest where the overlay happens to move around the most — which is where propagation-only methods fail hardest. The additive-conditioning design keeps the token sequence length unchanged, so the compute cost of the aggregation is a preprocessing step rather than a per-step overhead inside the transformer.
  • DVTE-Bench with OCR-screened clean targets.
    • Problem. A "clean" video that still contains residual text (watermarks on the clean copy, non-overlay text in-scene) contaminates reconstruction metrics: the model is penalized or rewarded for text that was never the removal target.
    • Mechanism. Candidate (overlaid / clean) pairs are run through OCR on the clean side, and any clean target with detected text is rejected. 569 candidates were rejected by this audit to produce the final 1,631-clip set.
    • Why it works. This makes Mask LPIPS and Mask VFID comparable across methods: the ground truth in the masked region is guaranteed free of distracting text content, which is otherwise a confound that favors methods with permissive text-generation priors.

Ablations

  • Full ablations on region weighting, visibility normalization, and additive conditioning are referenced in the paper; the specific numbers were not available in the HTML surface rendered without JavaScript for this review.

Microsoft

Self-Evolving Coding Agents via Harness-Policy Optimization (Self-HPO)

Tier 2 · Research Paper arXiv · Microsoft Research 2026-10-16 (arXiv) Coding agents · RL · Harness · Self-improvement

Overview

  • Microsoft Research (Zhepei Wei, Wenlin Yao, Baolin Peng, Danqing Wang, Qianhui Wu, Hao Cheng, Yu Meng, Jianfeng Gao) released Self-HPO on arXiv as 2610.22791 on 2026-10-16.
  • Core claim: coding agent performance depends on both the policy model and the harness (scaffolding that mediates its interaction with the environment); optimizing either alone leaves gain on the table, because a harness tuned for one checkpoint may miss the failures of an updated policy. Self-HPO alternates harness and policy optimization in a single loop.
  • Headline numbers: Qwen3.5-35B-A3B's average resolve rate across SWE-Bench Verified, SWE-Bench Multilingual, and SWE-Bench Pro rises from 57.8% to 64.8%, with gains preserved on out-of-distribution settings. Using Opus 4.8 as the harness proposer adds a further boost.

Methodology

  • Self-HPO loop. Alternates two steps per round:
    • H-step (harness). The current policy analyzes its own failure traces and proposes new harness candidates — the model is its own harness proposer. Candidates are then selected via a validation-set probe.
    • P-step (policy). The policy is updated with reinforcement learning under the selected harness. Hard tasks surfaced during training become the search set for the next round's harness proposal, so the harness search remains aimed at the current policy's live failure modes.
  • Benchmarks. SWE-Bench Verified, SWE-Bench Multilingual, SWE-Bench Pro — three variants spanning English single-language, multilingual code, and higher-difficulty tasks.
  • Policy backbone. Qwen3.5-35B-A3B (35B total, 3B active). The paper also reports the stronger-proposer condition using Opus 4.8 as the harness-proposer only (the policy is still the Qwen backbone).
  • Base agent comparison. Harness-only and policy-only baselines are the paper's control conditions; the joint gain is reported against the sum of their individual gains.

  • Out-of-distribution gain preserved. The paper reports gains carry over to OOD settings beyond the training task distribution.
  • Compositionality. Each optimized component (harness, policy) keeps its gain when paired with the base counterpart; the joint gain exceeds the sum of the individual gains.
  • Pass@k frontier shift. Both Pass@1 (reliability) and Pass@k (capability frontier) improve over the base agent, so the policy update is not only pruning the sampling distribution to a few lucky trajectories.

Named Contributions & Mechanisms

  • Policy as its own harness proposer, alternated with on-policy RL.
    • Problem. Coding-agent papers split into two camps. One optimizes the policy (SFT + RL on code-task rollouts); the other optimizes the harness (prompt-and-tool-wiring search, often with a separate "proposer" model). Both leave a residual gap because the two components interact: a harness tuned to a weaker policy over-scaffolds the stronger one; a policy trained under a weaker harness learns to compensate for scaffolding it no longer needs. Running both searches in parallel ignores this coupling.
    • Mechanism. Self-HPO runs sequentially: the current policy proposes harness candidates by analyzing its own failures (H-step), the best candidate is selected, and then the policy is updated with RL under that selected harness (P-step). Hard tasks surfaced during the RL rollout become the search set for the next H-step. The policy proposes the harness that targets its own current failure modes, and the subsequent RL pass then specializes under exactly that harness.
    • Why it works. This closes the Google Harness² loop (arXiv:2610.14224, 2026-10-09) one step further: Harness² keeps the policy weights frozen and iterates only the harness; Self-HPO co-updates both. The co-update means each H-step probes a different policy than the previous round, so the harness search never over-fits to a stale checkpoint. The Qwen3.5-35B-A3B jump of +7.0 pp on average across three SWE-Bench variants, with OOD transfer and compositional gain exceeding the sum of parts, is the paper's load-bearing evidence that the coupling is real.
  • Hard-task recycling across rounds.
    • Problem. Harness search needs a search set that reflects the current policy's failure distribution; a fixed held-out set over-represents the problems the policy already solves after a few P-steps.
    • Mechanism. Hard tasks found during the P-step's RL rollouts are collected and become the H-step search set for the next round. The search set thus tracks the policy's failure modes as they shift.
    • Why it works. Without this recycling, a late-round harness search picks over problems the policy already handles, and the H-step gain shrinks to noise. With it, each round's harness update is aimed at the problems the policy actually still gets wrong. The compositional result — joint gain beats sum of parts — is also the signature of this effect: the harness-only and policy-only baselines never see each other's hard-task residues.
  • Stronger-proposer condition using Opus 4.8.
    • Problem. The self-proposer condition is capped by the policy's own ability to diagnose its failures and suggest harness changes — a weaker policy is a weaker proposer. For a frontier-scale policy that is nearly as good as any available model, that is fine; for a mid-scale open policy, it is not.
    • Mechanism. The H-step proposer is swapped for Opus 4.8 while the policy backbone remains the open Qwen model. The RL (P-step) update is unchanged; only the harness-proposal LLM differs.
    • Why it works. This decouples the two capability axes: the policy carries the per-token inference cost at serving time, while the proposer only runs during the training loop. A frontier proposer can see failure patterns the policy itself cannot articulate, which widens the harness search in ways that then transfer to the (cheaper) policy via the P-step. The additional boost over the self-proposer condition is unquantified in the arXiv abstract.

Ablations

  • Harness-only vs policy-only vs joint ablations are the paper's primary ablation grid; the joint gain exceeds the sum of individual gains.
  • OOD transfer: gains preserved on out-of-distribution settings (specific OOD split not named in the abstract).
  • Compositional transfer: each optimized component retains its gain when paired with the unoptimized counterpart, which is the paper's argument against claims that the gain lives entirely in cross-component overfitting.

Other

  • Author overlap with 2026-10-19 ByteDance DeOverlay paper (none; Microsoft Research author list is disjoint).
  • Positioning vs 2026-09 Alibaba Mobius decoupled-knowledge-and-reasoning (prior 2026-08-17 review): Self-HPO is a joint-optimization pattern that assumes a monolithic policy; Mobius was a decomposition of the policy itself. The two are complementary and could be stacked.
