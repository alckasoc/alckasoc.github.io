IntBMoE: Integrating Block-Level Conditioning into Expert Composition for Full-Participation Mixture-of-Experts

Tier 2 · Research Paper arXiv 2026-09-19 MoE · Hypernetwork composition · Vision Transformer · Sequential recommendation · Production deployment

Overview

  • Ran Cheng, Longfei Xu, Zheng Liu, Kaikui Liu, Xiangxiang Chu (DreamX, Alibaba Group; Longfei Xu, Zheng Liu equal contribution; Longfei Xu project lead). arXiv:2609.21346v1 [cs.LG]. Code released at AMAP-ML/DreamX-Rec. Alibaba (Qwen and adjacent generative teams under Alibaba Group) qualifies under the frontier-labs filter.
  • The framing: a conventional MoE layer conflates three quantities that ought to be independent. Participation is how many experts contribute knowledge to a token's output; execution is how many are actually computed (a compute cost, O(k) forward passes for Top-k); materialization is how many expert-sized parameter sets must be built and stored at runtime (a memory cost). Sparse Top-k routing (Switch, GShard, DeepSeekMoE) keeps execution and materialization low but shrinks participation to k per token. Dense output-mixing (MMoE, PLE, Soft MoE, μMoE) restores full participation but scales execution with the number of experts E. Parameter-merging (SMEAR, Lory) keeps execution at one expert but its materialization grows with the number of distinct routing decisions G, at O(GE|θ|) synthesis cost per layer.
  • Contribution: IntBMoE, a block-conditioned MoE that pairs dense expert composition with sparse block execution, plus DPRG (Dual-Path Residual Gating), which couples two independently composed paths through multiplicative gating. Evaluated on ImageNet-1K, MiniPile causal LM, and IntTravel sequential recommendation; fully deployed in AMap's generative POI recommender under a 60 ms latency budget with a +2.4% relative UVCTR gain in A/B testing.

Methodology

  • Named contribution — IntBMoE (Integrated Block-conditioned MoE).
    • Problem. The three MoE strategies each break one axis: sparse-routing binds participation to execution, dense output-mixing binds execution to the pool size E, and parameter-merging binds materialization to the number of routing units. Existing designs cannot decouple all three because they conflate constructing an expert transformation with executing it on the input, so token-conditioning either fires the whole pool or reduces to a per-token synthesis cost.
    • Mechanism. IntBMoE replaces the FFN sublayer in a Transformer block with two-stage computation. Stage 1 (block-level parameter synthesis, token-independent). A codebook of K learned embeddings {cb∈Rdc} defines K reusable L-internal-layer blocks. A shared hypernetwork hφ (Linear–LayerNorm–ReLU trunk + two linear heads) maps each cb to a pair of composition coefficient vectors αbv, αbg ∈ RE for the value and gate paths. The coefficients are not normalized by softmax or sigmoid, so they can be negative and need not sum to one; a 1/E variance-preserving factor is applied when composing. For each internal layer ℓ the composed weight matrix is Wb,p(ℓ) = (1/E) Σe αb,ep We(ℓ) from a layer-specific pool P(ℓ)={We(ℓ), be(ℓ)} of E expert bases. Stage 2 (token-level Top-k routing). A two-layer ReLU MLP router gblock-router: Rd → RK scores the K blocks per token and selects the Top-k. Before entering a selected block, the token xt is filtered by a sigmoid mask mt,b conditioned on the block's codebook embedding cb, giving different blocks distinct views of the same token. The token then flows sequentially through the L composed layers of block b. Selected block outputs are weighted by softmax routing probabilities πt,b and added to an always-active shared SwiGLU expert path.
    • Why it works / why it beats prior. Every composed block draws on the entire expert pool, so participation is full (unlike sparse Top-k). The router still activates only k of K blocks per token, so execution stays sparse (unlike dense output-mixing). The codebook bounds the number of materialized composed blocks to K, independent of token count or routing unit count (unlike token-level SMEAR or segment-level Lory, which pay O(GE|θ|)). Composition depends only on model parameters, so at inference all K composed block parameters can be precomputed and cached, removing the O(KED) composition term from the request-time path.
  • Named contribution — DPRG (Dual-Path Residual Gating).
    • Problem. Each composed path Wb,p(ℓ) is a linear combination of the same expert bases. If a block used a single composed path, its output would be linear in the pool, and increasing the codebook or the routing granularity would not add expressiveness above what a shared FFN plus a linear per-block scaling could achieve.
    • Mechanism. Compose the expert bases twice per internal layer, into a value path vt,b(ℓ) and a gate path gt,b(ℓ). Apply RMSNorm to the gate path and SiLU to a learnable residual scale λ. Multiplicatively modulate: 𝝛t,b(ℓ) = vt,b(ℓ) ⊙ (1 + λ SiLU(gt,b(ℓ))). LayerNorm is applied between consecutive internal layers.
    • Why. The product of two independent linear compositions of the same expert basis is nonlinear in that basis, so DPRG adds expressiveness without enlarging E. Component ablations show that removing the gate path is the single largest regression on both ImageNet-1K (Top-1 0.7376 → 0.6804, −5.72 pp) and MiniPile (PPL 14.59 → 15.89).
  • Complexity accounting. Let each block contain L internal layers with total matrix size D = Σℓ dℓ-1 dℓ. Composition costs O(KED) once per weight update; routed execution over T tokens with Top-k selection costs O(TkD). Amortized per-token cost is O(KED/T + kD). At inference with cached composition, the request-time cost collapses to O(TkD), plus lower-order router / filter / shared-expert terms, and is independent of E. This is the key production property: expanding the expert pool is free at request time.
  • Default configuration (K, E, k, L) = (8, 16, 2, 2) across the visual, language and recommendation experiments. Codebook embedding dim dc and hypernetwork hidden dim dh tuned per task; two-layer blocks (L=2) win over parameter-matched one-layer blocks on every task. Coefficients are unconstrained (variance-scaled by 1/E) — softmax-normalized coefficients underperform on all three tasks.

Evaluation & Results

  • ImageNet-1K primary benchmark. 8-layer DeiT-Tiny-style backbone trained from scratch, mean over three seeds. IntBMoE reaches 0.7376 Top-1 and 0.9148 Top-5 at 24.30 M total parameters, 23.11 M activated, 4.063 GFLOPs per image (batch size 1) uncached and 3.457 GFLOPs cached. Relative to the dense backbone (0.6640 / 0.8769 at 3.94 M), gains are +7.36 and +3.79 Top-1 / Top-5 percentage points. Relative to SMEAR at matched total params, gains are +1.98 and +1.15. IntBMoE outperforms every sparse-routing baseline (Switch, DeepSeek-V3 MoE, ReMoE, V-MoE, Expert Choice, DynMoE, MASS) and every dense-participation baseline (Soft MoE, SMEAR, Lory, μMoE CP/TR).
  • Full-pool participation is empirical, not just architectural. Removing individual expert bases from all block compositions in one MoE layer (with a 1/(E−1) scale correction) and re-evaluating the ImageNet checkpoint without retraining lowers Top-1 accuracy by a mean of 1.60, 0.49, 1.17, 0.78 percentage points across Layers 0/2/4/6. Layer 0 concentrates: removing E1, E12, E15 drops accuracy by 4.10, 4.99, 9.15 pp respectively, versus much smaller effects for other bases; later-layer contributions are more evenly distributed (Layer 2 range 0.26–0.74, Layer 4 0.60–1.95, Layer 6 0.45–1.04). Even the smallest drop is 0.26 pp — every basis contributes.
  • Block-specific composition recipes differentiate with depth. Value-path mean pairwise cosine similarity between the eight blocks' composition recipes decreases monotonically 0.796 → 0.079 → 0.019 → 0.010 from Layer 0 to Layer 6; gate-path follows 0.726 → 0.126 → 0.083 → 0.043. Class-conditioned block-allocation heatmaps on eight ImageNet classes show that different classes favor different blocks at Layer 4 (e.g. hen prefers b4, Boston bull prefers b6) and these preferences shift by Layer 6 (b0, b3). Shallow layers mostly share expert-composition patterns; deeper layers construct block-specific recipes.
  • Component ablations (ImageNet-1K, Top-1).
    • w/o Gate (drop DPRG multiplicative modulation): 0.7376 → 0.6804, −5.72 pp. Largest regression.
    • 1-Layer (collapse two-layer block into a single parameter-matched layer): 0.6878, −4.98 pp. Two-layer block structure provides benefits beyond parameter count.
    • Fixed λ=1 (non-learnable residual scale): 0.7244, −1.32 pp.
    • Softmax Coeff. (constrain composition coefficients): 0.7263, −1.13 pp. Confirms unconstrained variance-scaled coefficients matter.
    • w/o Shared (drop the always-active shared SwiGLU expert): 0.7332, −0.44 pp.
    • w/o Filter (drop block-conditioned feature filtering): 0.7372, −0.04 pp.
  • Sensitivity to hyperparameters. Increasing K from 8 to 32 raises Top-1 by only +0.07 pp; increasing E from 16 to 64 raises it by only +0.15 pp. Increasing k consistently improves accuracy; k=2 is the reported default trading gain for per-token compute. Block depth L=2 maximizes Top-1.
  • Generalization to causal language modeling and sequential recommendation. On MiniPile (18-layer Llama-style causal Transformer, 6 GB deduplicated Pile subset), IntBMoE reaches PPL 14.5878 at loss 2.6802, a −2.9% PPL reduction versus μMoE CP (PPL 15.0306) and −12.4% versus the dense backbone (PPL 16.6621). On IntTravel (162.8 M users, 7.3 M POIs, 4.13 B interactions, "Where"-next-POI task), IntBMoE is best on HR@1 (0.6852), HR@5 (0.8692), and NDCG@5 (0.7850); every listed MoE baseline is at least one metric behind.
  • Caching decouples inference cost from expert-pool size. Peak inference memory for cached IntBMoE stays flat at 104.33 MB and inference cost stays flat at 3.457 GFLOPs per image as E grows from 1 to 128. Uncached inference scales as expected: memory 54.57 MB → 627.83 MB and compute 3.495 GFLOPs → 8.305 GFLOPs. Caching adds a fixed pre-materialization cost, so it becomes memory-favorable from E ≥ 16; training amortizes composition once per minibatch.
  • Production deployment. Cached IntBMoE serves AMap's initial-map POI recommender on Alibaba T-Head PPUs. Existing production model (no MoE) as control, cached IntBMoE as treatment, one-week online A/B experiment at approximately 5,000 QPS. Latency: average 19 ms, P99 38 ms, both within the 60 ms serving budget. Business metric: +2.4% relative UVCTR. Post-experiment, IntBMoE was fully rolled out to production traffic.

Trading Depth for Time in Recurrent Transformers

Tier 2 · Research Paper arXiv 2026-09-18 Latent Recurrent Transformer · Thought tokens · Depth–time trade-off · MoE · Test-time compute

Overview

  • Zeyi Huang, Xuehai He, Yong Jae Lee (University of Wisconsin–Madison), Yelong Shen (Microsoft). arXiv:2609.21605v1 [cs.LG], submitted 2026-09-18. Microsoft affiliation (Yelong Shen) qualifies this under the frontier-labs filter. Builds on the same authors' Latent Recurrent Transformer (LRT; arXiv:2605.26797) and directly compares against PonderLM-2 (Zeng et al. 2025) and looped Transformers.
  • The framing: a Transformer's computational depth per token can be increased in three ways. Physical depth adds independently parameterized layers. Looped Transformers repeatedly apply a shared stack (R loops of an L-layer backbone = RL layer executions per token with fixed parameters). Recurrent Transformers feed the preceding token's final hidden state into the current token's computation, extending computation along the temporal axis; the current token's forward pass builds directly on the preceding token's already-completed representation. This paper isolates the fourth degree of freedom: within a recurrent Transformer, is additional compute better spent as more temporal steps or as more physical layers?
  • Contribution: latent thought tokens inserted between consecutive vocabulary tokens in the LRT, sharing the LRT's backbone parameters and providing one extra stage of hidden-state refinement before the next-vocabulary-token prediction. Studied on 16-layer and 20-layer NanoChat MoE backbones (0.8B and 1.3B total parameters); one thought token recovers 67% and 81% of the BPB improvement from doubling LRT depth at approximately 48% fewer total parameters. Feedback ablations localize the LRT-with-thought-tokens advantage to the cross-token recurrent connection rather than to the thought-token computation itself.

Methodology

  • Named contribution — Latent thought tokens for LRT.
    • Problem. LRT feeds the preceding token's final hidden state ht-1 into the current token's computation, so one backbone forward pass per vocabulary token still traverses a longer recurrent dependency chain than a standard Transformer. Increasing computation from that starting point can be done by adding independently parameterized layers (more parameters, more distinct transformations), or by reusing the existing backbone for extra temporal steps (fewer parameters, but repeated shared transformations). The two allocations have never been controlled against each other at matched decoding block count within the same recurrent architecture.
    • Mechanism. Insert K continuous thought positions between each pair of consecutive vocabulary tokens. Let ht(0) be the state after processing vocabulary token xt and ht(j) the state after the j-th thought token. Then ht(0) = Fθ(E[xt], ht-1(K), C<t,0) and ht(j) = Fθ(ht(j-1), ht(j-1); C<t,j) for j=1,…,K. The two occurrences of ht(j-1) in the second equation have different roles: it replaces a token embedding at the input and supplies the recurrent feedback within the backbone. Thought tokens have no learned token embedding, share the backbone attention / MoE / feedback-projection parameters (only their feedback scales and gates are separate), and share their associated vocabulary token's rotary position index (indices 0,0,1,1,… for K=1; 0,0,0,1,1,1,… for K=2). All positions write KV states visible to later positions under the causal mask. The output head reads ht(K) to predict xt+1; setting K=0 recovers vanilla LRT. Block executions per vocabulary token during decoding: Bdecode(L, K) = L(K+1); one thought token matches doubling depth, two matches tripling depth, at the same block count.
    • Why it works / why it beats prior. The MoE router can learn to select different experts for vocabulary and thought positions at different thinking steps, so successive shared-backbone passes activate different subsets of the shared parameters. Against looped Transformers, thought-token LRT still has the cross-token feedback that Looped Transformers lack. Against PonderLM-2 (which also inserts continuous thought tokens), the difference is that LRT with thought tokens feeds the final thought state directly into the next vocabulary token's computation via the recurrent feedback pathway, so the explicit recurrent dependency chain continues across vocabulary-token boundaries. This is where the improvement over PonderLM-2 lives — the ablation below removes exactly that connection and finds the gap collapses.
  • Named contribution — Parallel Multi-Refinement Training for LRT with thought tokens.
    • Problem. The sequential-decoding equations require each position to wait for the preceding position's final state, so a straightforward parallel forward over the sequence is not possible. Naively unrolling the recurrence during training is prohibitively expensive.
    • Mechanism. Multi-refinement training (Zeng et al. 2025; Huang et al. 2026): each pass processes all positions in parallel, taking recurrent inputs from the preceding pass's final states shifted by one position. For thought-token models, these positions belong to the expanded vocabulary-and-thought sequence, and at thought positions the shifted state also supplies the input-embedding replacement. LRT with thought tokens: one vocabulary-only initialization pass with zero recurrent input (no direct prediction loss), then four refinement passes over N(K+1) positions; next-token loss applied in each supervised pass with equal weight; gradients retained across passes. In LRT with thought tokens, the prediction is read from the last thought state of each vocabulary-token interval, so the vocabulary position itself receives no direct prediction loss. PonderLM-2's multi-refinement uses 4.5 passes on average; looped Transformers instead unroll their repeated backbone passes in the training graph. Training-budget comparison across recurrent and looped runs is approximately — not exactly — FLOP-matched.
    • Why. This makes the recurrent gradient dependency chain trainable. Figure 2 of the paper illustrates a gradient path from a thought token in Refine 3 through a vocabulary token in Refine 2, a thought token in Refine 1, and a vocabulary token in initialization — four backbone passes and approximately 4L computational depth across two vocabulary-token intervals.
  • Setup. NanoChat MoE at L0=16 (0.8B reference) and L0=20 (1.3B reference). Depth multipliers 1×, 2×, 3× correspond to 16/32/48 and 20/40/60 layers respectively. MoE: 8 routed experts, top-2 routing, one shared expert. Width fixed across depth-scaled variants. LRT adds approximately 4% and 5% parameters over the reference vanilla Transformer through its feedback machinery; thought tokens reuse the same backbone and add no parameters. Evaluation: validation bits per byte (BPB, lower better) averaged over three seeds; sequential recurrence with KV caching from the first vocabulary token; models with one and two thought tokens are trained separately and evaluated with the same K.

Evaluation & Results

  • One thought token vs. doubling depth (matched decoding block count). At 16-layer reference, doubling LRT depth improves BPB from 0.798 to 0.780 (Δ=−0.018) while adding one thought token reaches 0.786 (Δ=−0.012). At 20-layer reference the corresponding values are 0.762 → 0.741 → 0.745 (Δ from vanilla LRT: −0.021 and −0.017). One thought token recovers 66.7% and 81.0% of the doubling-depth BPB reduction, leaving gaps of 0.006 and 0.004 BPB. Total parameters: thought-token models are at 1.04×/1.05× of the reference; double-depth LRTs are at 2.00×/2.04×. Both alternatives execute 2× the reference number of blocks per vocabulary token during decoding.
  • Two thought tokens vs. tripling depth. Going from one to two thought tokens improves BPB from 0.786 → 0.779 at 16L and 0.745 → 0.739 at 20L using essentially the same parameters as one thought token. Triple-depth LRTs reach 0.771 and 0.731 BPB. LRT with two thought tokens comes within 0.008 BPB of the triple-depth LRTs at both sizes, recovering 70.4% and 74.2% of the tripling-depth improvement while using approximately 65% fewer total parameters (1.04×/1.05× vs 2.96×/3.03×).
  • Comparison with looped Transformers. At two backbone forward passes per vocabulary token, LRT with one thought token beats the two-loop Transformer by 0.018 BPB at 16L and 0.029 at 20L. With two thought tokens, gaps over three-loop Transformers are 0.020 and 0.029. LRT with one thought token also beats the four-loop model at both sizes. The 4–5% LRT parameter overhead is small relative to these gaps.
  • Comparison with PonderLM-2. With one thought token: 0.786 (LRT) vs 0.797 (PonderLM-2) at 16L, 0.745 vs 0.752 at 20L. With two: 0.779 vs 0.789 at 16L, 0.739 vs 0.745 at 20L. LRT wins at all four combinations.
  • Comparison with standard Transformers. LRT with one thought token beats a triple-depth (48-layer / 60-layer) standard Transformer despite using fewer total parameters and fewer decoding block executions: 0.786 vs 0.789 at 16L, 0.745 vs 0.756 at 20L. This is a parameter-and-decoding trade-off comparison rather than a training-FLOP-matched claim, since the standard Transformer runs use less training compute.
  • Cross-token recurrence ablation localizes the gain. Remove the connection that feeds the final thought state into the next vocabulary token's computation while retaining the thought-token computation itself. BPB at 16L increases from 0.786 to 0.795 (+0.009), approaching PonderLM-2's 0.797. The explicit cross-token recurrent chain is the key contributor to the LRT-with-thought-tokens advantage over PonderLM-2. Information still flows through causal attention, so this is not simply an information-loss effect — it is the depth of the recurrent dependency chain.
  • KV feedback ablation. Remove KV feedback (project keys and values from ht-1) while retaining hidden-state feedback and cross-token recurrence. BPB at 16L increases from 0.786 to 0.790 (+0.004). KV feedback provides an additive benefit beyond the hidden-state residuals alone.

Ablations

  • Feedback ablations at depth 16 with one thought token (Table 2 of the paper): full LRT 0.786; without cross-token recurrence 0.795 (+0.009, approaches PonderLM-2's 0.797); without KV feedback 0.790 (+0.004); PonderLM-2 reference 0.797 (+0.011). Removing cross-token recurrence alone closes most of the LRT-vs-PonderLM-2 gap, isolating the longer recurrent dependency chain across token boundaries as the dominant contributor. KV feedback provides an additional smaller benefit on top of hidden-state feedback.

Other

  • Limitations named in the paper. Deeper LRTs remain better than thought-token LRTs at the same decoding block count — independent layers provide capacity that repeated shared transformations do not fully replace; the experiments do not isolate the cause. Training budgets across recurrent and looped runs are approximately, not exactly, FLOP-matched. Decoding block counts omit attention overhead; equal block counts do not imply equal FLOPs or latency because thought-token models attend over more positions and incur greater attention interaction cost. Models with different numbers of thought tokens are trained separately, so generalization to more thought tokens or adaptive thought-token counts at inference is left open. The recurrent source is the final-layer hidden state rather than a searched intermediate layer; a searched intermediate layer is left for future work.
  • Frontier-lab context. Microsoft (Yelong Shen and collaborators) has been one of the frontier labs pushing test-time-compute-via-latent-thought architectures over the last year; this paper is the follow-up to their earlier LRT release (arXiv:2605.26797), directly comparing the depth and temporal axes within the same recurrent architecture and reporting a decisive ordering of feedback-design choices. No Microsoft frontier model launch is announced in the paper.
