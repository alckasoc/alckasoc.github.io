MobilePA-Bench: Benchmarking Mobile Planner Agents on Complex Real-World Tasks

Tier 2 · Research Paper arXiv 2026-08-24 Agent benchmarks · Mobile agents · Tool use · Planning · Interactive sandbox

Overview

  • Yi Zhu, Xiongwei Wu, Qiyi Wang, Tingyu Qu, Jiajun Liu, Sihan Cao, Long Chen, Weigao Sun, Feida Zhu, Yiran Zhong, Steven Hoi et al. (Alibaba Tongyi-MAI, the mobile-AI subgroup of Tongyi Lab) release MobilePA-Bench, an interactive, stateful, tool-centric benchmark for evaluating the tool-calling and planning abilities of mobile planner agents. arXiv:2608.23035v1 [cs.AI], submitted 2026-08-24, on the Hugging Face Daily selection for 2026-08-25.
  • The framing: two existing benchmark families each have a blind spot. GUI-centric benchmarks test surface-level screen manipulation but overlook background tool-use and long-horizon planning; static function-calling benchmarks rely on offline API-signature matching that is detached from real runtime constraints (permission scopes, tool ordering, transient failures, live state). MobilePA-Bench replaces both with an executable sandbox that maintains live application databases and returns structured feedback so that success is measured against observed state transitions rather than string-matched call transcripts.

Methodology

  • Named contribution 1 — interactive, stateful, tool-centric mobile sandbox.
    • Problem. On mobile, the tools a planner has to orchestrate are a mixture of GUI actions, background system APIs, and third-party app calls; a benchmark that hard-codes the expected sequence, or that scores against a static function-signature list, cannot distinguish agents that produce a plausible-looking call from agents that actually change the world in the correct way. Without live state, effects like “the calendar event now exists,” “the message was actually sent,” or “the permission dialog was granted the correct scope” cannot be verified.
    • Mechanism. MobilePA-Bench runs on an executable sandbox that hosts 13 functional domains and 212 realistic mobile tools with live application databases. Each tool invocation mutates real backing state; each attempt is evaluated by evidence-based verification over that state (whether the expected records exist, whether unintended writes occurred, whether the response actually references the correct retrieved facts) rather than by name-matching against a golden call sequence. The sandbox returns structured feedback that the agent can consume mid-trajectory.
    • Why it works / why it beats prior. By moving evaluation from surface transcripts to persistent state, the benchmark scores end-to-end task completion. Agents that produce clean-looking tool calls but leave the wrong state, extra state, or missing state fail; this is exactly the failure mode that GUI-only and static-function benchmarks miss. The stateful sandbox also decouples evaluation from any single agent stack — a planner that decomposes into sub-agents, a planner that emits shell-like skill invocations, and a planner that drives raw GUI clicks are all scored on the same downstream state.
  • Named contribution 2 — three planner-agent evaluation axes beyond basic tool-calling.
    • Problem. Function-calling accuracy alone does not predict whether an agent can run a real mobile copilot workload — users delegate compound tasks (“book me a flight, notify the calendar, notify the group chat”) that hit sub-agent orchestration, cross-session memory, and pre-packaged skills. Prior mobile benchmarks score isolated calls and miss the composition.
    • Mechanism. Beyond basic tool-use, MobilePA-Bench evaluates the central planner along three additional dimensions: (i) Sub-agent collaboration: decomposing a complex user request and delegating specialised subtasks to capable sub-agents; (ii) Memory usage: recalling stored memories, user profiles, and past preferences to resolve implicit requests (references to entities never named in the current turn); (iii) Skill usage: invoking pre-packaged composite skills instead of planning every step from scratch when a matching skill exists. Each dimension has its own task pool and evidence-based checks; task-specific executable checks accept valid trajectories while rejecting wrong, missing, or extra effects.
    • Why it works / why it beats prior. Splitting evaluation along these axes attributes failures. A model that scores well on basic tool-use but collapses under sub-agent collaboration is failing at planning, not at tool call formatting; a model that scores well on skill usage but poorly on memory usage exposes a specific gap that a targeted training recipe can address. The alternative — one bulk pass/fail number — conflates all three failure modes, which is the axis on which MobilePA-Bench improves over static function-calling and GUI-only benchmarks.
  • Named contribution 3 — strict runtime perturbations (tool ordering, permission limits, unexpected errors).
    • Problem. Real mobile environments enforce tool ordering (some calls only make sense after prior state exists), permission scopes (some tools return partial data when permission is limited), and transient failures. A benchmark that runs each task in a clean, fully-permissioned, error-free environment overstates agent reliability.
    • Mechanism. The benchmark injects strict tool-ordering constraints, permission-scope limits, and unexpected runtime errors, and re-scores agents under those perturbations. Results show current frontier LLMs remain unreliable in mobile settings and drop sharply under each of these conditions.
    • Why it works / why it beats prior. Directly measuring the delta between clean-environment and perturbed-environment success rates isolates the robustness gap that would otherwise only show up in production incidents. Because the sandbox is stateful, the perturbations compose with the evidence-based verification — a permission-scoped tool call that returns partial data and an agent that acts on the partial data as if it were complete is caught by the state check even when the tool call itself looks well-formed.

Evaluation & results

  • Task pool: 13 functional domains, 212 realistic mobile tools, executable sandbox with live application databases and structured feedback. Scoring: task-specific executable checks that accept valid trajectories while rejecting wrong, missing, or extra effects.
  • Headline finding: current frontier LLMs remain unreliable in mobile settings. Performance drops sharply under strict tool ordering, permission limits, and unexpected runtime errors. The paper positions this as evidence that clean-environment pass rates on prior mobile benchmarks over-report deployable reliability by conflating tool-call-plausibility with state-change correctness.
  • Cross-benchmark context: the pattern (frontier models with adequate clean-environment scores collapsing once environment perturbations or long-horizon state are introduced) is consistent with the Thinkingbox result on business workflows (best model 65.36% pass@1 → 25.25% pass20 on 507 policy-conditioned workflows) and with the failure-mode signature reported in the recent stateful-tool-use line.

Other

  • Positioning: MobilePA-Bench is pitched as both (a) a practical diagnostic benchmark for mobile planner agents and (b) an interactive foundation for agentic reinforcement learning — the same stateful sandbox that scores an agent can serve as an RL environment for training one. This is the same framing pattern as Thinkingbox (“sandbox and benchmark”) and the Kimi K3-vintage agent RL environments.
  • Coverage: 13 functional domains span messaging, calendar/contacts, media, navigation, retail-adjacent categories, and system-level tools; 212 tools are described as realistic in the sense of matching the shape of live mobile APIs rather than synthetic function signatures.

Towards a Densing Law for User Representation Learning at Billion-Scale Capacity

Tier 2 · Technical Report arXiv 2026-08-24 Scaling laws · User representation · Tokenization · Recommender models · Alipay

Overview

  • Bin Dou, Junru Zhang, Zhaoyi Yuan, Wuliang Huang, Letian Gong, Baokun Wang, Huan Li, Yu Cheng, Weiqiang Wang (Ant Group, on the billion-scale Alipay dataset) release a 28-page, 13-figure technical report proposing the User Behavioral Densing Law and an accompanying adaptive variable-length tokenizer ALGN. arXiv:2608.23392v1 [cs.IR], submitted 2026-08-24, on the Hugging Face Daily selection for 2026-08-25.
  • The framing: industrial user representation is scaled by growing three axes — user count, behavioural sequence length, and model size. At billion-scale capacity, feeding raw text user behaviour into the encoder hits diminishing returns; switching to tokenized behaviour restores sustained gains, but there is no quantitative rule for how the tokenization configuration should be co-scaled with the input data size. The paper’s claim is that this rule exists, is empirically log-linear, and can be used to pick a minimum-sufficient tokenizer configuration for a given data budget instead of over-provisioning it.

Methodology

  • Named contribution 1 — the User Behavioral Densing Law.
    • Problem. Raw-text user-behaviour input scales poorly at billion-user capacity: gains from adding more raw behavioural tokens diminish sharply, so the marginal token adds no representation quality. Prior scaling analyses (Chinchilla-style compute-optimal, and the 2024–2026 densing-law line on parameter–capability compression) do not specify the tokenizer axis, so practitioners either over-provision tokenizer capacity (wasting representation slots) or under-provision it (leaving quality on the table).
    • Mechanism. The paper runs a pilot billion-scale Alipay-corpus study comparing raw and tokenized scaling, then, through combined theoretical analysis and systematic experiments, derives the densing pattern: the logarithm of the minimum sufficient tokenization capacity is approximately linear in the logarithm of input data size (measured in tokens). The slope of that line is not universal: it varies systematically with the tokenization method and the data source, and that variation is attributed to differences in representation-space redundancy and intra-source uniqueness (a source whose events collapse to few equivalence classes needs less tokenization capacity per additional token than a source with many distinct atomic events).
    • Why it works / why it beats prior. A log-linear rule turns tokenizer selection into a two-parameter fit per (method, source) pair — the slope explains how much capacity a new token buys, the intercept anchors the starting point — so a practitioner can predict the minimum tokenizer configuration for a given target data scale rather than searching over configurations at every scale. This is the axis on which the paper improves over prior densing-law work: prior work compressed model size against downstream capability but did not include the input-side representation (tokenization) as a co-scaled variable.
  • Named contribution 2 — ALGN: adaptive variable-length tokenization for user behaviour.
    • Problem. Fixed-length behavioural tokenizers (BPE-on-events, item-id tokenization) allocate the same number of code slots to every user regardless of how much idiosyncratic behaviour that user actually exhibits, so users at the sparse tail waste capacity while users at the dense head starve for it. The Densing Law makes this concrete: since minimum-sufficient tokenization capacity is a function of input token count, the tokenizer should adapt per-sequence, not sit at a globally fixed budget.
    • Mechanism. ALGN is a variable-length behavioural tokenizer whose code allocation grows with the sequence in the shape prescribed by the Densing Law — long, information-dense behavioural traces receive more codes than short or repetitive ones, along the log-linear axis identified in the law. The tokenizer is used as the front-end of the same billion-scale user-representation encoder trained on the Alipay corpus.
    • Why it works / why it beats prior. Capacity allocation matches the theoretical minimum-sufficient curve rather than sitting above or below it uniformly; the paper reports that ALGN outperforms existing baselines across diverse data sources, tokenization methods, and downstream tasks. The pipeline advantage — law-derived, then engineered — is what makes the tokenizer generalise: the same slope-and-intercept relationship holds across sources, so the same adaptive rule transfers without per-source retuning.

Evaluation & results

  • Pilot study: raw vs tokenized scaling comparison on the billion-scale Alipay dataset. Raw-text behavioural input exhibits diminishing gains with larger scale; tokenized input delivers sustained gains at the same scale. This is the empirical wall the law is built to explain.
  • Law fit: an approximately linear relationship between log(minimum sufficient tokenization capacity) and log(input data size in tokens). The slope varies systematically with tokenization method and data source; the paper attributes slope differences to representation-space redundancy and intra-source uniqueness.
  • Downstream: ALGN, the law-derived adaptive variable-length tokenizer, outperforms existing baselines across diverse data sources, tokenization methods, and downstream tasks. The scope of “diverse” is stated at the abstract level of “across sources / methods / tasks”; the 28-page technical report contains the per-source, per-task numerical breakdown across 13 figures.

Ablations

  • Slope decomposition by tokenization method and data source: the paper documents how slope differences correlate with representation-space redundancy (higher redundancy → flatter slope, since additional tokens buy less capacity) and intra-source uniqueness (more unique atomic events → steeper slope). This is the empirical hook that lets the Densing Law transfer from Alipay-scale to other corpora without a full re-fit — only the two per-(method, source) parameters need re-estimation.

Other

  • The report is 28 pages / 13 figures / cs.IR; positioning is against the recommender-systems scaling literature and the 2024–2026 densing-law line rather than against LLM-vintage compute-optimality curves. The user-side signal — behavioural events on a payments/lifestyle platform at Alipay scale — is a distinct data regime from web text, and the paper argues that this regime is where the tokenizer axis becomes the bottleneck rather than model size or sequence length.
