Architecture

  • MoE backbone (unchanged from preview). 770B total parameters, 49B active per token excluding MTP (~780B / 49.7B when MTP is counted). Granular top-8 routing from 256 routed experts plus one always-on shared expert; this is close to DeepSeek-V4's and GLM-5's routing density, but routing weights are disjoint from either.
  • Gated DeepSeek Sparse Attention (Gated DSA). Low-rank MLA-style query / KV compression (q_lora_rank 2048, kv_lora_rank 512, qk_nope_head_dim 192, qk_rope_head_dim 64, v_head_dim 256) plus a lightweight indexer with 32 indexer heads, 128-dim indexer, and index_topk 2048. The config.json flags use_mla: true, use_dsa: true, gated_mla: true, learnable_sink: true.
  • IndexCache. The sparse selection produced by the indexer at each layer is cached and reused by downstream layers rather than recomputed, moving the indexer off the per-layer critical path. The preview repo cites arXiv 2603.12201 as the IndexCache reference.
  • Identity Hyper-Connections (iHC). The residual stream is widened from a single path to 4 parallel streams (hc_mult=4); enable_ihc is set in config.json. Each stream carries its own hidden representation between blocks, and layer operations route across the four streams rather than collapsing them. This is an inter-layer information-flow widening, not an attention-head change.
  • MTP (multi-token prediction) head. 1 native layer at 10B total / 0.7B active. Serving config exposes it directly: vLLM --speculative-config '{"num_speculative_tokens":3,"method":"mtp"}', SGLang NEXTN with 3 steps, top-k 1, 4 draft tokens.
  • Context. max_position_embeddings 1,048,576, rope_theta 10,000,000. The full release reports no change to context length over the preview.
  • Vision stack (new in full release). Tencent's launch post says Hy4 "introduces visual understanding for the first time"; the encoder architecture (ViT vs patch-projection, encoder parameter count, patch size, image/video max resolution), training data mix, and vision-only benchmarks are not disclosed in the Nov 4 launch materials. Vision support is confined to the full release; the preview's tencent/Hy4-preview and tencent/Hy4-preview-FP8 checkpoints remain text-only.
  • Reasoning control. reasoning_effort defaults to "high"; "no_think" disables it. Recommended sampling: temperature 0.9, top_p 1.0.

Named Contributions & Mechanisms

  • Gated DeepSeek Sparse Attention (Gated DSA).
    • Problem. A 1M-token context under dense softmax attention produces a KV cache whose size and per-layer read cost dominate decoder latency; prior sparse-attention variants (block sparse, sliding-window, Mamba-style linear) trade retrieval sharpness for cost, which hurts frontier coding and tool-use benchmarks where the model must resolve references anywhere in the context.
    • Mechanism. Inside every attention layer Hy4 computes two projections: an MLA-style compressed query/key path (q-LoRA rank 2048, kv-LoRA rank 512) that carries the sharp retrieval signal at compressed rank, and a lightweight indexer (32 heads, 128-dim) that scores all positions and picks the top 2048 keys. Softmax attention is then computed only on those 2048 keys; the rest of the context is dropped for that layer. The "Gated" in Gated DSA refers to a learnable gate that scales the sparse attention output against a learned residual sink (learnable_sink: true), so the layer can fall back to a predictable sink when the top-2048 selection is inconclusive.
    • Why. Keeping MLA's compressed-rank KV cache preserves the retrieval sharpness that full-rank MHA gives on long context, while the indexer collapses the per-layer attention cost to O(2048 d) rather than O(n d). Compared to DeepSeek-V3's MLA (which paid full-rank attention over the chosen rank's KV cache) and GLM-5's linear-plus-sparse hybrid (which lost retrieval sharpness at the block boundaries), Gated DSA keeps softmax retrieval active per layer and lets every layer re-select its own sparse set — which is where IndexCache below picks up.
  • IndexCache.
    • Problem. Per-layer selection in DSA runs the indexer 78 times (once per layer) over the full 1M-token context at decode time, which turns the indexer itself into a cost center. On short contexts the indexer is cheap; on 1M tokens it is not.
    • Mechanism. After an indexer layer fires, its top-2048 selection is written into a shared cache. Downstream layers reuse the cached selection instead of recomputing the indexer from scratch, concurrently with their own attention over the already-selected keys. The cache is invalidated on new generation steps (not on every layer), so the indexer runs only on prefill plus a small number of refresh points during long decodes.
    • Why. This decouples the indexer's wall-clock cost from the layer depth and pushes it toward O(1) amortized per decoded token on long context. The config.json's index_n_heads=32 and index_head_dim=128 are sized so that even the cold indexer pass is cheap; the warm path through IndexCache is essentially free. It is the piece that makes a 1M-token context economically viable for a 49B-active model served at $0.834/M input.
  • Identity Hyper-Connections (iHC) with hc_mult=4.
    • Problem. A single residual stream across 78 layers limits how much orthogonal information can flow from early layers to late ones; later layers must either overwrite earlier residuals or compress them, and both are documented failure modes on very deep MoE stacks.
    • Mechanism. The residual is widened from one stream to 4 parallel streams, each carrying its own hidden representation between blocks. Attention and FFN operations project across the four streams (not head-wise, not layer-wise). Early layers can write to one stream and late layers to another; identity connections preserve the uncompressed signal path along each stream between blocks.
    • Why. Compared to Hy3's single residual (reviewed indirectly in the 2026-02 Hy3 release) this gives Hy4 a roughly 4× wider inter-layer information channel at the cost of 4× residual memory, which matters for a 78-layer stack but barely registers against the 1M-token KV cache budget. It is why Hy4 can carry out long chain-of-thought + computer-use + vision together without a visible interference regime: each capability's representations can occupy a different residual stream.
  • Native MTP speculative head.
    • Problem. Open-weight model serving at 49B active is still memory-bandwidth-bound on decode; a text-generation request at frontier quality sees no benefit from the big MoE backbone if token-by-token decode is serial.
    • Mechanism. A dedicated 10B-total / 0.7B-active MTP layer at the output head proposes the next 3 tokens in a single forward pass. The main model verifies the proposal and accepts a longest-matching prefix. vLLM exposes this as method="mtp", num_speculative_tokens=3; SGLang exposes it as NEXTN, 3 steps, top-k 1, 4 draft tokens. The MTP head is co-trained with the main model, so its proposals are high-acceptance on in-distribution text (not a separate draft model).
    • Why. This is the same trick DeepSeek-V3/V4 use, but Hy4's MTP layer is sized larger than DeepSeek's (10B total vs ~1B for most speculative drafts) and uses the same tokenizer and attention mechanism as the main model, giving higher acceptance rates on long code and tool-call sequences. The acceptance rate is not published; Tencent reports "near-linear decode speedup" but no concrete tokens/second figure.
  • Computer-Use skill (full release).
    • Problem. Open-weight models have had no first-party answer to Claude Sonnet 5.5's and Gemini 4 Argon's closed computer-use benchmarks; third parties who wire open models to screen-capture pipelines ship brittle agents whose action spaces drift between desktop OS and web browser.
    • Mechanism. Tencent combines command-line and GUI actions into a single action space the model is trained on end-to-end, rather than two separate output heads. The model's output at every step is either a command-line call (bash-like, routed to a sandboxed shell) or a GUI action (click, type, scroll, hotkey — coordinates issued in screen-relative units). A single training objective covers both, with BookingAgent and EmailAgent as the first published target scenarios. Action-space cardinality, training-corpus size, and sub-step credit assignment are not published.
    • Why. Keeping command-line and GUI in one action space means the same post-training pass transfers between terminal workflows (where the model knows how to type git) and desktop apps (where it must click). A two-head approach would require either two post-training stages or a hard-coded router between them, both of which Tencent avoids.

SWE-Trail: History-Guided Trajectory Collection for Coding Agent Training

Tier 2 · Research Paper arXiv · Ant Group (inclusionAI) + UConn 2026-11-01 Agentic coding · Trajectory collection · SFT data curation · SWE-bench

Overview

  • Ziming Li (Ant Group + UConn), Lu Yu, Jiatan Huang, et al. publish SWE-Trail as the trajectory-collection stage of Ant Group's Ling-3.0 coding-agent training pipeline (Ling-3.0-flash-base-124B is the primary target student; Qwen3-14B-Base is the secondary verification).
  • The paper's central claim is that where alternative trajectories are sampled from matters more than how many resolved trajectories you get. On a controlled 300-issue SWE-rebench V2 collection with five trajectories each, SWE-Trail-H5 lifts SWE-bench Multilingual by +2.33 and SWE-Pro by +1.60 over the SeedBank baseline; SWE-Trail-H0 (same algorithm, no history input) lifts by only +0.11 / +0.73, even though it produces more resolved trajectories than SeedBank.
  • SWE-Trail is also an explicit critique of advice-in-context methods like SWE-Exp, which show prior attempts to the agent at collection time: the student then learns actions it took under advice it won't have at test time, and the paper measures a -1.33 / -2.78 regression under this paradigm.

Methodology

  • Setup. 300 SWE-rebench V2 issues. For each issue, 5 independent trajectories are collected per method, giving 1,500 trajectories per method. Collection agent: GLM-5.1 with the OpenHands scaffold. Student: full-parameter SFT on 128 H800 GPUs, 3 training seeds per condition.
  • Offline compiler stage. For each issue the method reads a history H_i (either H0 = empty history, H5 = five prior attempts from SeedBank, or H10 = ten), runs bounded read-only repository checks (no reference patch), and freezes an acquisition record R_i = (D_i, u_i, λ_i): a detector D_i over actions and observations (not step numbers), a per-state comparison objective u_i(d), and a temperature schedule λ_i. Detector states without sufficient support are discarded before collection runs.
  • Online collection stage. The agent runs on the issue as normal. When D_i matches an in-progress state, the agent samples k candidate next actions from its ordinary context: the first candidate uses the agent's default temperature; the remaining k-1 use the compiled λ_i schedule. Equivalent proposals are grouped; at most one executable alternative to the default is kept. Two isolated workspaces are then restored from the same checkpoint and each runs a short horizon, producing two executed suffixes. At most one such comparison is allowed per trajectory.
  • Selector. The two suffixes are shown to the selector (an LLM judge) in shuffled order. The alternative replaces the default only when the evidence under u_i(d) is "clear"; otherwise the default suffix is kept.
  • Training-record assembly. Only the selected route is written out, unrewritten. The unselected suffix and all collector-internal events (detector matches, candidate rankings, counterfactual rollouts) are stripped, so the final training record is one continuous agent trajectory — history never enters the agent's context at train time or test time. This is the design point that distinguishes SWE-Trail from SWE-Exp.
  • Data flow volumes. H0 yields 329 resolved trajectories at ≥1.845B training tokens; H5 yields 345 at 1.914B; H10 yields 341 at 2.160B.

Named Contribution & Mechanism

  • SWE-Trail (two-stage offline-then-online collector with detector-gated counterfactual branching).
    • Problem. Sampling k independent trajectories per issue produces redundancy at the roots and diversity only at the tails. Expected solved issues on SWE-rebench V2 rise from 58.4 at k=1 by only +13.1 (k=2), +8.0 (k=3), +5.1 (k=4), +3.4 (k=5). Patch-target coverage per attempt is already 73.2–90.0%, so additional roots mostly re-discover known fixes. Existing fixes are advice-in-context (SWE-Exp, which regresses), post-hoc rewriting (SWE-Lego, SWE-TRACE), or scale-only (SWE-Gym). None of those move the training signal to where the trajectory's branching matters.
    • Mechanism. The compiler reads history once, offline, and freezes an acquisition record R_i = (D_i, u_i, λ_i) for each issue: a detector D_i over actions and observations (not step indices, so it transfers between agents), a per-state comparison objective u_i(d) that scores how "better-supported" an alternative is at each eligible state, and a temperature schedule λ_i that controls the alternative-sampling spread. At collection time the agent runs normally; when D_i matches, the compiler forks two isolated workspaces from one checkpoint, executes a short horizon under the default suffix and under one alternative, and the selector keeps the alternative only when u_i says the evidence is clear. Only the chosen route is written to the training record; history and the unchosen suffix are stripped.
    • Why. Decoupling collection-time branching from the agent's own context closes the train-test mismatch that SWE-Exp introduces (student doesn't see history at test time, so it must not be trained to need it). Restoring two workspaces from one checkpoint keeps the counterfactual honest — both suffixes run from identical state, so the selector's comparison is on execution outcomes rather than on sampled tokens. Doing the comparison at detector-matched states instead of at random positions means collection effort goes into decisions whose outcome the paper has evidence actually matters (ablation: random-state comparisons lose -1.44 / -1.28 vs H5; random-retention at those states loses -0.89 / -1.19). The paper's own numbers show the gain does not come from more resolved trajectories or more training tokens: H0 produces 12.7% more resolved trajectories than SeedBank, and gains +0.11. The gain comes from the branching mechanism.

Ablations

  • Random detection (comparisons at random eligible states, no detector): 64.22 / 41.54 — H5 loses -1.44 / -1.28 without the detector.
  • Random retention (random executed route kept at the right states, selector disabled): 64.78 / 41.63 — H5 loses -0.89 / -1.19 without the selector.
  • H10 vs H5. +0.22 / +0.14 for +12.9% more training tokens — sharp diminishing returns past five history attempts.
  • Top-5 selection variants. Top-5-of-10 selection: 64.11 / 41.86. Top-5-hybrid (mixing on-method and best-overall): 66.22 / 43.14.
  • Advice retention. Removing advice from the final training record improves SWE-Pro and slightly lowers Multilingual (direction only; appendix numbers not transcribed in the fetched HTML).

Limitations

  • Three seeds. The exact one-sided permutation p = 0.05 is the floor achievable with three vs three runs, so the test is minimally powered. H5-vs-H0 task-paired bootstrap intervals include zero.
  • Scale. Only 300 SWE-rebench V2 issues at 5 trajectories each; the paper does not run the full collection at order-of-magnitude larger scale, so whether the gain holds past 1500 trajectories is untested.
  • No SWE-bench Verified or DeepSWE numbers in the fetched text, so the comparison to the canonical English-only suite and to the current open-weight SWE SOTA (DeepSeek-V4.1-Flash-1017 77.0, Meta Muse Spark Open ~68) is not in the paper.
  • Collection agent is GLM-5.1, not a frontier model. The paper does not test whether SWE-Trail's gain holds when the collection agent itself is stronger (plausibly the collector's default suffix becomes harder to beat).
