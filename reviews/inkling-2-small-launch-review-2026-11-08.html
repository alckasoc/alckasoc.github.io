Thinking Machines Lab

Inkling 2 Small

Tier 1 · Launch Post + Model Card thinkingmachines.ai 2026-11-05 Flagship launch · MoE · Agentic RL · NVFP4 training

Overview

  • Thinking Machines Lab's first flagship model, positioned as a coding- and agent-leaning general model. Inkling 2 Small is a 594B-parameter Mixture-of-Experts with 17B active parameters, 48 decoder-only transformer layers, and a vision encoder; text and image input, text output.
  • Served via Tinker for both inference and fine-tuning. The news post states that full weights will come "next week" under Apache 2.0 after safety testing; the live model card currently lists the license as "Tinker Terms of Use," so weights are closed at launch.
  • Companion artifact: a model card with benchmark tables and an architecture section. There is no accompanying arXiv technical report; the recipe details are distributed between the news post, the model card, and a promised NVFP4-training follow-up.

Architecture

  • MoE backbone. 48-layer decoder-only transformer. 384 experts per MoE block with top-8 routing per token; 17B of 594B parameters active on any given forward pass (≈2.9% activation ratio).
  • Attention. Hybrid local/global attention — the model card describes the standard sliding-window + full-attention interleave used in the current generation of long-context MoEs. Supports up to 1,048,576 tokens of context.
  • Vision encoder. 292M-parameter encoder derived from a Perception Encoder-style ViT, operating on 20×20-pixel patches with 2×2 patch pooling before projection into the LM embedding space. Text + image input; no audio or video modalities.
  • Numerics. Weights are stored and trained in MXFP8 for most layers and NVFP4 (the 4-bit floating-point format introduced with Blackwell) for selected matmuls. The post claims this is the first large model trained natively in NVFP4; a separate recipe post is promised. Inference also exposes an NVFP4 path.

Pre-training

  • Four staged pretraining horizons (H1–H4):
    • H1 — 8.4T tokens at the base context length.
    • H2 — 3.8T tokens at 512K context, extending the model into long-context regime.
    • H3 — ~320B tokens of reasoning and agent trajectories at the full 1M context.
    • H4 — ~34B tokens of agent trajectories, used as a bridge into post-training.
  • The post notes that H3/H4 trajectories were drawn from the lab's agent harness so that long-context pretraining distribution already matched the deployment distribution — rather than following a post-hoc context-extension recipe applied to a short-context base.

Post-training

  • Problem. Running separate reasoning-style RL and agentic/tool-use RL typically produces two specialized checkpoints that regress on each other's axis and require a merge or interleave schedule that is itself a hyperparameter forest.
  • Mechanism — single joint RL run. One continuous RL training run of 1,075 optimization steps over 9 days on 2,048 GPUs (>4×10²³ FLOPs) jointly trains against reasoning rewards and agent/tool-use rewards. Rollouts are drawn from a single rollout fleet feeding a single policy. The post names this as the main novelty of the recipe: no separate "reasoning model then agent model" phases, no interleaving schedule.
  • Why it works. The ablation claim is that separate runs create goal interference during whichever run runs second; a joint run with per-trajectory reward attribution routes gradient updates cleanly by rollout type. No specific head-to-head numbers are shared in the news post; the follow-up recipe post is promised.
  • Trajectory-level grader. Instead of only a terminal reward on whether a code task passes, Inkling's RL loop uses a process grader that scores how the model approached the task — intermediate decision points, tool choices, backtracking behavior. This is a per-trajectory reward shaper, not a value head; the news post does not disclose the grader model.
  • Alignment stack. Three ingredients: (1) misbehavior-filtered midtraining — a data-level pass that removes misalignment-adjacent completions before SFT; (2) a general alignment reward mixed into the RL run; (3) on-policy self-distillation from a conduct-spec teacher — the policy is distilled against its own rollouts filtered by a teacher that encodes Thinking Machines' conduct spec.

ByteDance Seed

SAE Interprets MoE: Sparse AutoEncoders Reveal That MoE Experts Exhibit Human-Interpretable Fine-Grained Specialization

Tier 2 · Research Paper arXiv:2611.08089 2026-11-05 Interpretability · MoE · Sparse autoencoders

Overview

  • Anyuan Zhuo, Shaohua Zhang, Yuan Lin, Pinyan Lu (ByteDance Seed, inferred from the Bytedance-Seed GitHub org hosting the code and SAEs).
  • The paper reframes MoE expert analysis away from "how often is each expert selected on domain-labeled corpora" and towards "how much does each expert actually contribute to the latent features the layer encodes." The vehicle is a sparse autoencoder trained on the layer's output.

Methodology

  • Problem. Classical MoE specialization studies count the gating weight each expert receives on a domain-labeled corpus. This conflates routing (the gate's decision) with contribution (the expert's effect on the layer output), requires a predetermined domain taxonomy, and gives coarse labels ("math," "code") rather than the sub-concept features the layer actually computes.
  • Mechanism. Let the MoE layer output on token t be y_t = Σᵢ g_i(t) · E_i(t), the router-weighted sum of expert outputs. Train an SAE over y_t: a latent's pre-activation is an affine function W·y_t + b, which pushes linearly through the sum, so each latent's pre-activation decomposes exactly into per-expert contributions Σᵢ g_i(t) · (W·E_i(t)). Aggregating absolute contribution over a corpus gives each expert a dominant set of latents it is the primary driver of.
  • Why it works / why it beats prior. Where gating-based analyses conflate "chose this expert" with "this expert mattered to the output," the decomposition isolates actual output contribution. The affine property of the SAE encoder is what makes the decomposition exact — a nonlinear probe would break this clean decomposition. The resulting unit of specialization is a latent feature, not a hand-chosen domain, so the taxonomy comes from the SAE dictionary rather than from the analyst.

Evaluation & Results

  • Model studied. Qwen3-30B-A3B at layers 4, 30, and 46 — one early, one mid, one late. The abstract reports per-expert contribution concentration is materially sharper than the gating distribution: most latents have one or two dominant experts rather than diffuse participation across the active-k set.
  • Overlap structure. Dominant-set overlap between pairs of experts is not uniform — it concentrates on a small number of expert pairs, consistent with the experts organizing into functional clusters rather than independent specialists.
  • Auto-interpretation. The paper runs a prompted LLM over each expert's dominant-latent activations and surfaces sub-domain splits the usual coarse analyses miss: separate experts for Java vs. front-end web code, and for geometry vs. arithmetic/polynomials.
  • Headline-number tables are not disclosed in the abstract; the detailed per-layer and per-expert statistics are in the body (not yet fetched here).

Other

  • Open-sources code and the trained SAEs at github.com/Bytedance-Seed/SAE-Interprets-MoE, which makes this one of the first public SAE suites trained on a frontier open-weight MoE.
  • Scope limit: the analysis is per-layer, static per corpus; it does not yet characterize how expert specialization evolves through training or across fine-tuning.

Google

Muir: Linear Attention with Sensitivity-Allocated Gating and Matched-Filter Readout

Tier 2 · Research Paper arXiv:2611.08376 2026-11-05 Architectures · Linear attention · Long context

Overview

  • Tushaar Gangavarapu (UT Austin), Gil Tabak, Clemens JS Schaefer (cjsschaefer@google.com, corresponding author). A three-author linear-attention architecture paper framed as a diagnostic-plus-redesign of Gated DeltaNet-2 (GDN-2).
  • Two moves: replace GDN-2's dense full-rank gates with a sensitivity-allocated low-rank projection, and replace unweighted state readout with a matched-filter readout gate. Saved parameters go to a wider FFN.

Methodology

  • Problem. GDN-2's state recurrence S_t = (I − k_tᵀ(b_t⊙k_t)) · Diag(α_t) · S_{t−1} + k_tᵀ(w_t⊙v_t) uses dense full-rank erase gate b ∈ (0,2) and write gate w, which together consume 2d² of the per-layer parameter budget (≈12d² total) — compressing the FFN by >25%. At inference, slow-decaying state rows accumulate large norm and dominate unweighted readout. Chunkwise kernels also fail at wide matmul sizes because cumulative-decay division under/overflows.
  • Mechanism — sensitivity-allocated gating. The paper proves (Prop. 3.1) that layer output sensitivity to the erase gate is strictly lower than to the write gate; erase can therefore be low-rank without harming the forward pass. All gates are fused into one low-rank projection with ranks apportioned by per-gate sensitivity — erase gets fewer, write gets more. The erase logit decomposes as a low-rank term plus a per-channel bias.
  • Mechanism — matched-filter readout. Queries are reweighted per state row before readout, combining a static channel profile with a dynamic per-token gain. The optimal gain scales as λ_j^(ℓ/2) for a retrieval lag ℓ and decay λ_j, matching the state row's expected decay. This equalizes state rows and lowers the erasure needed to prevent cross-row interference.
  • Mechanism — boundary-pivoted chunk kernel. Splits relative decays without division, eliminates the full-chunk 3D decay tensor, and solves within-chunk triangular systems with block matmul. Stays numerically stable at the large chunk sizes that wide-matrix accelerators (TPU, H100 with tensor cores) prefer.
  • Why it works. Writes affect every channel; erasure is active only where keys are active, so an erase gate has lower output sensitivity and can be cheap. Reallocating the saved parameters into FFN width is where most of the perplexity gain comes from, with the matched-filter readout giving a separate bump on extractive-recall tasks.

Evaluation & Results

  • Scale sweep. 166M → 1.34B parameters. Across all scales: perplexity 1.8–2.0% lower than GDN-2 and 2.5–3.6% lower than Transformer; commonsense zero-shot accuracy up by up to 1.9 points.
  • Long context. At 1.34B parameters, trained at 4K context, Muir extrapolates to 10M-token streams without perplexity drift. Passkey retrieval holds near 100% up to 1M tokens.
  • Training efficiency. Reaches GDN-2's 100B-token validation loss 1.2× faster; trains 2.7× faster than Transformer at 32K context length and 1.64× faster than Transformer at 16K. Throughput at inference matches GDN-2.
  • NLL deltas (Fig. 1). Muir is 18.0–20.4 millinats better than GDN-2 and 25.0–36.2 millinats better than Transformer in validation NLL across scales.

Ablations

  • Fig. 1 attribution: the low-rank gating + FFN expansion ablation drives most of the perplexity delta over GDN-2; matched-filter readout drives the extractive-recall delta specifically.
  • Rank-allocation ablation (Section 5.3 of the paper, referenced in the abstract): sensitivity-allocated ranks beat uniform-rank splits at matched parameter budget.

Other

  • Limitations are not stated explicitly in the fetched portion of the paper; the 10M-token extrapolation is reported without a corresponding compute cost, and training-cost claims are at matched token counts rather than matched wall-clock on the same hardware.

NVIDIA

VFlash: Fast, Accurate Visual Planning via Flash Primitive Decoding

Tier 2 · Research Paper arXiv:2611.08449 2026-11-05 Robotics · VLM decoding · Speculative decoding · World action models

Overview

  • Yu-Cheng Chou, Shihao Wang, Jin Huang, et al. (NVIDIA; co-authors include Johan Bjorck, Linxi "Jim" Fan, Jan Kautz, Zhiding Yu, and Sifei Liu — all NVIDIA-affiliated). 18 authors total.
  • Target problem: autoregressive VLMs generate visual plans (bounding boxes, point trajectories, 3D motion tracks) coordinate-by-coordinate, so richer plans cost proportionally more sequential forward passes. VFlash collapses each primitive's coordinates into one draft pass.

Methodology

  • Problem. Writing a bounding box as "<box> u1 v1 u2 v2 </>" is four sequential decoding steps for coordinates alone. A 32-point trajectory is 64 steps (2D) or 96 steps (3D). Plans that a robot or driving policy consumes are therefore bottlenecked on the per-token loop, not on compute. Classical speculative decoding (DFlash-style) accepts a draft only where its tokens exactly match the target's greedy continuation (Eq. 2 in the paper) — token-level agreement does not measure spatial accuracy, so a near-miss draft that would still be a correct plan is rejected.
  • Mechanism — Flash Primitive Decoding (FPD).
    • Base model: Qwen3-4B language backbone + a native-resolution MoonViT vision encoder + an MLP connector. Coordinates are encoded as 1,001 special tokens (image coordinates normalized to [0, 1000]).
    • Each primitive has a fixed layout determined by type and tool-call length (Table 1 of the paper): boxes have a 4-coordinate slot, 2D trajectories have P paired slots, 3D trajectories have an interleaved 2D+3D block.
    • A five-layer non-causal block drafter runs over frozen target-model features. On a primitive-start token, the drafter predicts all B(s)−1 downstream coordinate positions of that primitive in a single forward pass (Eq. 3). Supervision is a uniform-weighted cross-entropy against annotated coordinates — not against the target model's continuation (Eq. 4), which is what unblocks learning spatially-correct but token-divergent plans.
    • At inference: 16-position DFlash blocks run until a primitive-start token is accepted; the FPD drafter then produces the whole primitive block. Per-position logit constraints enforce the primitive's layout. Boxes get an extra guard: a LocateAnything-based spatial-confidence check; failed boxes fall back to constrained AR decoding, so accuracy never drops below the AR baseline.
    • Cost model (Eq. 6): L_dir = (t_par + t_target) / B(s). Sequential passes per primitive are constant in the primitive's size.
  • Why it works. Once primitive type and length are fixed, each coordinate position has a known role, so joint prediction is well-posed even without autoregressive factorization. The spatial-loss supervision means the drafter can beat its AR target on spatial error, not only tie it.

Evaluation & Results

  • 2D trajectories (Table 2 of the paper), VFlash vs AR at matched 4B target:
    • ShareRobot-Bench: Hausdorff Distance 0.162 vs 0.175, RMSE 0.133 vs 0.142.
    • VABench-V: HD 0.116 vs 0.125, RMSE 0.089 vs 0.093.
    • The paper reports VABench spatial error drops ~40% vs the best prior comparison, LoHo-Manip.
  • Bounding boxes (Table 3), F1 mean | BPS:
    • COCO: AR 48.68 at 3.15 BPS → VFlash with AR fallback 47.79 at 8.76 BPS.
    • Dense200: AR 60.10 at 6.73 BPS → VFlash with AR fallback 61.78 at 17.46 BPS.
    • Direct (no fallback) on Dense200: 39.09 F1 at 22.66 BPS — the fallback is what preserves precision at high density.
  • 3D trajectories (Table 4): AgiBot 3D-only success rate SR@5 improves from 0.503 (AR) to 0.731 (VFlash). Abstract reports ~25× faster 3D point motion forecasting, flagged as a preliminary single-rollout measurement.
  • Downstream — world action model. Using VFlash plans in a MolmoSpaces-trained world action model lifts average success from 62.6% → 70.2% across four task suites.

Ablations

  • Fallback vs direct boxes (Table 3): Dense200 mean F1 61.78 vs 39.09 — direct-only is fast but loses high-IoU precision; fallback recovers it at only a modest throughput cost.
  • Joint 2D+3D vs 3D-only training: AR's 3D ADE is 15–51% worse when forced to generate joint outputs; VFlash degrades much less.
  • Wrist-camera training: VFlash ADE drops 3–12% when wrist-camera frames are added to the training mix.
  • MolmoSpaces downstream: AR-generated plans reach 61.0 vs VFlash 70.2; swapping plan input for raw image context costs 6.5 points; 3D-only plans (no 2D) sit at 69.3.

Other

  • Limitations: box precision drops at IoU 0.95; the 25× figure for 3D point forecasting is called "preliminary" and comes from single-rollout measurements. Multi-primitive generation (drafting several primitives in one block) is named as future work.

The Components of Agent Memory

Tier 3 · Engineering Blog Post anthropic.com 2026-11-06 Agent memory · Dreaming · Wikis · Claude Code
  • Author: Lance Martin (Anthropic Engineering). Post summarizes empirical results across CL-Bench 1.0, Pokémon Red runs, an internal ~350,000-file ~420M-token wiki corpus, Harvey LAB merger questions, and a contract-terms wiki.
  • Memory architecture — four tiers. (1) Transcripts, a searchable event log of past sessions; (2) memory notes Claude writes during work; (3) memory representations (wikis, contract pages) compiled from notes; (4) injected context loaded into every session — MEMORY.md in Claude Code is the prototype (first 200 lines or 25 KB). Salience judgment (what to write down) is a cross-cutting ingredient, not a fifth tier.
  • "Dreaming" consolidation — mechanism. Offline passes over transcripts and notes that: (a) correct errors in existing notes, (b) merge duplicates, (c) build wikis from scratch, (d) promote items to injected context. The post does not disclose the trigger, cadence, or prompt; it says dreaming "requires compute" and is run as a background job. The fix pattern is adversarial self-review: Claude reads its own earlier notes and emits corrections.
  • Problem being solved. Fixed save-rules ("record only failures," "write everything") hurt stronger models — Opus 5 loses 0.234 on CL-Bench when told to record only failures. Letting Claude judge salience itself, with offline dreaming to repair drift, outperforms rule-based memory stacks.
  • CL-Bench 1.0 database task, mean reward, stateless → memory:
    • Opus 5.5: 0.655 → 0.838
    • Sonnet 5.5: 0.644 → 0.833
    • Opus 5: 0.564 → 0.828
    • Opus 4.7: 0.383 → 0.700
    • Sonnet 5: 0.306 → 0.610
    • Sonnet 4.6: 0.330 → 0.364 (0.641 with refined prompting)
  • Pokémon Red case study. Sonnet 3.7 wrote 413 memory files and earned 1 badge. Fable 5 wrote ≈10 files and earned 4 badges. More memory ≠ better memory. A corrected-by-dreaming Mt. Moon note let the agent reach Cerulean at action 1,935; the uncorrected note never escaped the mountain.
  • Wiki on 350K-file / 420M-token internal corpus, 25 questions, 128 dreaming sessions: wiki-only 13% → 48%; wiki+search 54% → 61% vs 53% for search-only.
  • Harvey LAB merger questions (24 items): wiki 87% vs. search 73%. Another LAB task showed "no clear gain" and one wiki grew to 1.77× the corpus size — compression inversion is a live failure mode.
  • Contract-terms wiki: going from one shared table to one page per contract lifted coverage from 41/57 facts (72%) to 57/57 facts (100%). The structural representation matters as much as the content.
  • Open questions named in the post: when to write memory during a run, how to keep a wiki current as the underlying corpus shifts, and whether salience judgment should be a learned per-token signal rather than a prompt-level discipline.
